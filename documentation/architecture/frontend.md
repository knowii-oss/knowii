# Front-end design

The front-end is a React 19 application rendered through Inertia.js 3. Laravel decides which page to show and with which initial data. React renders it, and talks to the REST API for every change.

## Pages

1. A page is a component in `apps/knowii/src/Pages/<Area>/<Name>.tsx`, rendered by an Inertia controller (`app/Http/Controllers/Inertia`) or by `Route::inertia(...)` in `routes/web.php` for static pages. The list of pages is `pageComponents` (`apps/knowii/src/page-components.ts`): it leaves the spec files out, so the production build never ships a spec file as a page (#1552).
2. The controller passes the initial data as props. The props interface of the page and the array in the controller must stay aligned (both carry a `WARNING` comment).
3. Every page renders inside `<AppLayout>`, which gives the header, the breadcrumb, the page actions and the footer. Community pages also render `<CommunityShell>` (`Components/Spaces`): the space navigation in a sidebar on desktop and in a drawer on mobile, reloaded when the space tree changes.
4. Further data and every change go through the Knowii API client, never through Inertia form posts. The API stays complete.
5. Links use Inertia `<Link>`. A link that changes the URL without a reload sets `preserveState={true}`.
6. A visitor (nobody signed in, `page.props.auth.user` is null) reads the public spaces through four pages: the space, the post, the page or lesson and the resource ([ADR 0044](../adr/0044-public-spaces-for-visitors.md)). `<AppLayout>` gives them "Sign in" and "Sign up" in place of the user menu and no dashboard link, and tells the components below it through `VisitorProvider` (`Components/Reader`). `<SignInPrompt>` ("Sign in to reply", "Sign in to post", "Sign in to download") takes the place of a composer or of the download. Reactions are counts, and no member name is a link. The props are cut by the server: the client never hides what it received. The public page of a community (#1485, `Pages/Communities/Public.tsx`) is the fifth page: a visitor and a signed-in outsider get it instead of the community home, with the name, the description, the navigation of the public spaces and the newest public posts, and the way in of an open community (#1486): `<JoinCommunity>` (`Components/Communities`) shows "Join" to a signed-in outsider and "Sign up to join" and "Sign in" to a visitor, on this page and in the header of a public space, and nothing for a member or when the community is by invitation (`community.join_policy`). It does not join by itself after a sign-up, keeps the focus while it works (`aria-busy` and a guard, never `disabled`) and shows the refusal of the server in an alert. The settings page has the card `<JoinPolicySetting>` (owner and admins) and the member management lists the removed members with "May join again". In the breadcrumb of a visitor "Home" goes to `/` (the layout does it), and the community to this page. A public space shows no notice to its members (#1493); the texts of the space form for a manager are in `Components/Spaces/PublicSpaceNotice.tsx`.

## Rendering errors

A component that throws while rendering does not blank the page. `<ErrorBoundary>` (`@/Components/ui`) catches the error, logs it to the console and shows a fallback:

1. `<AppLayout>` wraps the page content: the header, the navigation and the footer stay, the content shows "Something went wrong on this page" with "Try again" and "Reload the page". An Inertia visit to another URL clears the error (`resetKey={page.url}`).
2. `main.tsx` wraps the whole application, for an error in the layout itself.
3. Member content uses the block variant, so one broken item does not hide the others: each post card, the post body, each comment (`<ErrorBoundary variant="block" label="this post">`). Wrap new member content the same way (chat messages, pages, lessons).

## Global data

1. Data that every page needs (the current user, the communities of the user) comes from `HandleInertiaRequests`.
2. Client-side state that every page needs lives in the React context of `libs/common/src/lib/contexts/app-context.tsx`. Example: `showToast()`. The provider keeps the toasts, and the `<Toaster>` (mounted once in `main.tsx`) shows them. A toast survives an Inertia visit. A toast can offer one link to the next step (`action`, for example "Open the space" after a new space, #1576): it stays until the person follows the link or closes the toast, and when a toast that has the focus goes away, the focus goes back to the element that had it before.

## UI components

1. The building blocks live in `apps/knowii/src/Components/ui` and are imported from `@/Components/ui`: buttons, form controls, dialog, drawer, menu, select, cards, avatar, toasts and more ([ADR 0003](../adr/0003-own-ui-components.md)).
2. Use them instead of styling raw elements. A new building block goes there, with a Vitest test (`*.spec.tsx`), keyboard support and a visible focus ring.
3. Headless UI is used only for the accessible interactive parts (dialog, listbox, menu, switch). Everything else is plain React and Tailwind CSS.
4. Feature components (a post card, a space navigation) live in `apps/knowii/src/Components/<Feature>/` and compose the building blocks.
5. A setting that saves at once, without a "Save" button, is a `Switch` (#1569), with a `SaveStatus` next to it: "Saving", then "Saved", or the error, and the control shows the old value again (`useInstantSave` holds the value, the busy state and the status). A choice of several values that saves at once (who can join) keeps its radios and gets the same status. A `Checkbox` is only for a form with a "Save" button. A change that widens access (a community open to anyone with an account, indexing on) asks first with a `Dialog`: nothing is saved before the yes, and "Cancel" and Escape leave the control as it was.

### Toolkit

The building blocks have stories in Storybook ([ADR 0049](../adr/0049-component-toolkit-storybook-stories-as-tests.md), #657). The configuration is in `apps/knowii/.storybook/`.

1. Run it in the container: `npm run storybook` (the dev server on port 6006, open `http://localhost:6006` on the host; the port is `STORYBOOK_PORT` in `docker-compose.yml`) or `npm run storybook:build` (the static site in `dist/storybook`). The toolbar switches the theme (dark first) and the width (360 px, 1920 px). The accessibility panel checks the contrast, which the tests cannot do.
2. Add a story: create `Components/ui/<Name>.stories.tsx` next to the component, in the CSF 3 format with types (`satisfies Meta<typeof Name>`). Write one story per variant and state: kinds, sizes, with and without an icon, disabled and `aria-disabled`, busy, error, long text, as the component has them. The comment of the meta says when to use the component and its accessibility contract. A keyboard path is a `play` function that uses `storybook/test`, with `within(canvasElement)`, or `within(dialog)` for a dialog (it renders in a portal on the body, and jsdom does not make the page behind it inert).
3. The stories are tests: `stories.spec.tsx` renders every story, runs its `play` function and runs `axe-core` on the page, with the other Vitest tests. Only `color-contrast` is off, because jsdom computes no colors.
4. The guard, `stories-guard.spec.ts`, fails when a component file has no story file or a story file has no story. The components without a story yet are in its sorted allow-list: when you add the story file of one, remove its name from the list (the guard fails until you do).
5. A story renders without the application around it. The link stories of `Button` stop the Inertia visit in their `onClick`; do the same for another component that needs the application, without changing the component.

Member content: `MarkdownContent` shows the HTML that the server renders. It replaces each `div.video-embed` block (a YouTube or Vimeo link alone on its line, [ADR 0031](../adr/0031-videos-in-member-content.md)) with the click-to-load `VideoPlayer`. The `MarkdownEditor` has an "Add a video" button that checks the address with `parseVideoUrl` (`libs/common`).

Images in the editor (#1207): the image button, a paste or a drop takes up to 10 images at a time. `ImageInsertPanel` lists them with a preview, a required description (the alt text), the state of each upload, and buttons to reorder and remove. "Insert the images" uploads them one after the other and writes them one per line; nothing goes in the text before every upload worked, and a second try uploads only the images that failed.

Galleries ([ADR 0039](../adr/0039-images-that-follow-each-other-form-a-gallery.md)): the server writes the images that follow each other as `div.image-gallery`, with each image as a link to its file. The grid is CSS only (`.image-gallery` in `styles.css`, chosen from `data-image-count`), so there is no layout jump when the script starts. `MarkdownContent` listens to the clicks on its content and opens `ImageViewer` (Headless UI Dialog): the image on the whole screen, its alternative text as the caption, previous and next with the buttons, the arrow keys, Home, End and a swipe, and "Open the original". A click with a modifier key stays a normal link. A rich block that only needs a shared dialog follows this pattern; a block that needs its own component gets a React root, like the videos.

## Themes and tokens

1. Colors, fonts and breakpoints are the Knowii brand tokens defined with `@theme` in `apps/knowii/src/styles.css`. The default Tailwind palette is disabled. The Noto Sans font comes from the `@fontsource-variable/noto-sans` package: `main.tsx` imports its CSS and Vite bundles the WOFF2 files, so the font is served from the Knowii origin. Never load a font or a stylesheet from a font service (#1341, GDPR): the CSP allows none.
2. Two themes: dark (default) and light, selected with `data-theme` on `<html>`. The inline script in `app.blade.php` applies the saved choice before the first paint. `useTheme()` and `<ThemeToggle>` change it.
3. Tokens change with the theme: never hardcode `white` or `black`. Check every screen in both themes.

## Content Security Policy

The policy has no `'unsafe-inline'` for scripts or styles ([ADR 0007](../adr/0007-strict-content-security-policy.md)):

1. Set styles with classes, or with React `style` props (they go through the CSSOM, which the policy allows).
2. Never call `setAttribute('style', ...)`, and never add a `<style>` element without the nonce from `<meta property="csp-nonce">`.
3. Third-party scripts are added by our own code (`'strict-dynamic'`). Avoid embeds that inject styles.
4. Images, media, frames and connections go only to the origins listed in `config/secure-headers.php`.

## Data and validation

1. Zod schemas in `libs/common/src/lib/types` describe the entities (`community.schema.ts`) and in `libs/common/src/lib/api` the requests and responses (`create-space-request.schema.ts`).
2. Forms use react-hook-form with the Zod resolver. The limits come from `libs/common/src/lib/constants.ts`, aligned with `App\Constants`.
3. The Knowii API client (`libs/common/src/lib/api/knowii-api-client.ts`) is the only place that calls `fetch` for the API. API paths are constants in `constants.ts`. New methods use `apiRequest()` (`api-result.ts`): it parses `data` with a Zod schema and returns an `ApiResult` (`ok`, `data` or `message` and field `errors`), never throws.

## Real time

`useSocket` (`libs/common/src/lib/hooks/use-socket.ts`) wraps Laravel Echo. A page names a channel and the events it wants, and gets typed payloads. The event names match `broadcastAs()` on the back-end. Each hook removes only its own listeners when it unmounts, and the channel is left when its last user unmounts, so several components can listen on the same channel. A visitor opens no connection: the hook takes `enabled`, which a page or component sets to false for a visitor, and `window.Echo` (`bootstrap.ts`) is created on its first use, because creating it opens the connection. Pages merge incoming events into their state (by `cuid`, so a duplicate is ignored) without losing what the member is typing.

## Notifications: the bell and the panel

The bell and its panel (#1484, [ADR 0042](../adr/0042-notifications.md), design 5.1, 5.2, 6.12 and 9) are in `Components/Notifications`. They show "Needs you" and, since #1497, "Following" (the level 2 lines). `<AppLayout>` renders them for a signed-in member, on every page. A visitor gets no bell, no count request, no socket and no live region.

1. One source of truth for the number. `NotificationsProvider` holds the count, and the count is always the value of the server (`GET /notifications/count`). It is loaded on page load, when the window gets the focus, when the socket reconnects (`useSocketReconnected`) and after each `notifications.changed` event of the channel `user.{cuid}`. The client never adds 1. Events of a short time give one request (a trailing debounce of 300 ms), and a late answer never replaces a newer one. The bell name holds the number ("Notifications, 3 new", "Notifications, 9 or more new") and the badge (1 to 9, then "9+") is hidden from assistive technology.
2. The panel mounts when it opens, so each opening loads the list again (`use-notification-feed.ts`: 20 lines per page, "Load older", and "Earlier" behind a closed disclosure, loaded the first time it opens, never counted: the list that was "Older" before #1476). On a desktop it is a non-modal region under the bell: Tab leaves it, Escape and a click outside close it. Below the `md` breakpoint (960 px, the phone layout of the app) it is the `Drawer` component. The focus goes to the heading "Notifications" on opening, and back to the bell on closing.
3. A line is a list item with one link and real buttons (`NotificationLine`). The link goes to the exact item (`notification-link.ts`): `#comment-{cuid}` on the post page or the resource page (the permalinks of #1205), and `?thread={cuid}#message-{cuid}` on the chat space. `ChatRoom` follows that address: it opens the thread, or loads older messages (10 pages at most) until the message is there, and gives it the focus. The target of a jump keeps a visible outline until the focus leaves it. A line that is not seen yet shows "New" in bold, never by color alone. The word stays while the panel is open.
4. Seen: a line that stayed visible in the open panel for one second (an `IntersectionObserver`, or every line when the browser has none) is marked seen. One request holds all the lines of that moment, then the count is loaded again.
5. "Done" marks the row read and removes the line. The status text of the panel (polite) says "Done. Undo" for 8 seconds. "Undo" puts the line back; a 422 (a newer notification exists) reloads the list. The focus goes to the next line, else the line before, else the heading. The buttons of a line never use `disabled`: they use `aria-disabled` and `aria-busy` with a guard, and keep the focus.
6. An event while the panel is open never moves the list. Lines that arrived wait behind "2 new. Show". A line that another device marked done and that has the focus stays, marked "Done on another device", until the focus leaves it.
7. One polite live region exists from the load (in `NotificationsProvider`). It says the actor and the verb of a new level 1 row that the member did not see ("Ben replied to your post"), once per 30 seconds at most. Several arrivals of the window become "3 new for you". It never announces a change of the count. Nothing uses `assertive`.
8. With `prefers-reduced-motion` nothing slides or shimmers (the skeleton lines use `motion-safe:animate-pulse`, the `Drawer` has its own rule), and the jump to a comment or a message is instant.
9. The shared Inertia prop `communityCount` tells the panel whether to show the name of the community on each line (more than one community).
10. "Following" (#1497) is a second section under "Needs you", with its own feed (`useNotificationFeed({ following: true })`, `GET /notifications?level=2`: the last 14 days, no "Earlier"). Its lines are never counted by the bell and never announced. A line holds one sentence built from the kind and the live counts (`notificationSentence`: "3 new replies in <title>", "Ben posted in <space>: <title>", "4 new posts in <space>", "New messages in <space>", "Lesson <title> of <course> is out"), the space, the time and the word "New". "Stop following" is on the lines of a thread (`notification-thread.ts` finds the thread of a line). "I am caught up" is at the top of the heading when it has lines: one request (`POST /notifications/caught-up`) clears every "Following" line, never a "Needs you" line; the focus goes to the heading "Following" and the status text says "You are caught up".
11. The menu of a line (the `DropdownMenu` component, on "Needs you" lines too) holds "Mute this thread" (a line of a thread), "Mute <space>" and "Why did I get this?". The mute entries ask nothing: they apply at once, and the status text says "Muted. Undo" for 8 seconds (the undo of a thread calls `DELETE .../mute`, which gives back the exact earlier state, no row included, with no read before the mute; the undo of a space goes back to the earlier level; neither brings back the lines that the server deleted). A line of the kind `space_post` or `lesson_new` that bundles several items shows its sentence, the space and the time, and no title and no excerpt (`notificationShowsItem`, #1509); its accessible names hold no title either. "Why did I get this?" shows the reason as a sentence built from the `reason` code (`notificationReasonSentence`) and a link named after its setting ("Notification settings for <space>") that opens the settings page at that space. The menu opens in a portal outside the panel, so the panel ignores a click or an Escape that belongs to a menu.
12. Follow state and levels outside the panel. The state of a thread is loaded when the control mounts (`ThreadFollowControl`: `GET .../follow`, one request per page or per opened chat thread, never one per item): "Following (you wrote this)", "Following (you replied)", "Following", "Not following" or "Muted", with "Follow", "Stop following" and "Mute this thread". It is on the post page and in the chat thread panel, for a member of the community only (`community.is_member`). `SpaceLevelControl` (space page, members only, no link space) shows the level of the space with the sentence of each choice ("Everything" for a discussion space and a chat space only). Both save at once, say the result in a status region, and show `role="alert"` "Not saved. Retry." with the focus kept on the control when the server refuses.
13. The settings page `/user/notifications` (`Pages/Profile/Notifications.tsx`, route `profile.notifications`, entry "Notification settings" in the user menu) lists "Your spaces" per community: `GET /communities/{community}/notification-levels` once per community, one `fieldset` with a `legend` per space group, one `Select` per space labelled "Notifications for <space name>", and "Same for all spaces of this group" (one request per space that can take the level, then "Applied to N spaces"). One column, the label above the control, controls of 44 px. The page holds one status region ("Saved", cleared after 4 seconds so that the next "Saved" is announced again).
14. Managers get "What members get by default" in the space form (`default_notification_level`, sent only when changed; while the manager did not touch it, the field shows the built-in default of the current "Who can post" and follows it, #1509) and, when they can moderate the space, the post composer has "Tell the followers of this space now" (`notify_now`, off by default).

### Where I am (#1476, [ADR 0048](../adr/0048-where-i-am.md), design 5.2 to 5.5, 6.7, 9.3 to 9.9)

The screens of the server part. Everything here is for a signed-in member: a visitor has no provider, no pop-up, no card, no dot and no question about the zone.

1. The provider wraps the whole layout (`AppLayout`), not only the bell, so that the tab title, the pop-up and the cards share one source. It also holds `messages` (the conversations with new messages, from `GET /notifications/count`) and the opener of the panel (`registerPanel` / `openPanel`, used by "Show all" on the home).
2. The time zone. `AccountTimeZoneProvider` (in the layout) gives the zone of the account to `RelativeTime`, which shows its full date and hour in that zone with the zone named (`formatFullDateTime`); the relative text does not change. `TimeZoneAsk` (members only, in the layout): an account with `time_zone: null` gets the zone of the browser saved one time without a question (the only write without a click; `undefined` is an old session and is left alone); when the browser reports another zone it shows one plain region "Show times in <zone>?" with "Yes, use <zone>" and "Keep <zone>", never a dialog and never the focus, and remembers the answer per account and pair of zones in `localStorage`. The sign-up sends the zone of the browser in a hidden field. The settings page has "Your time zone" (`TimeZoneForm`) and the switch "Show pop-ups" (`PopupsForm`): both are saved at once with "Saved" and "Not saved. Retry." like the space levels, and reload the `auth` prop.
3. The tab title (`TabTitle`, replaces `<Head>` in the layout): "(3) <title>" with the bell number plus `messages`, "(9+)" above 9, nothing at zero, always the server value.
4. The pop-up (`NotificationPopup`, rendered by the provider): only for a new level 1 line (the same lines that the live region announces), only when the tab is visible, the switch is on, the panel is closed and the line is not the thread that is open (`notification-open-thread.ts`). One at a time: a second line within 30 seconds replaces it with "<N> new for you" (a link to the page "Notifications"). It stays 8 seconds plus 1 second per 20 characters (rounded up), 20 at most; the timer stops on hover, on focus inside and while the tab is hidden. One link and one close button ("Close the notification"), no live region of its own (the one polite region says it once), Escape only with the focus inside, at the top of the page (never over a composer or the bottom navigation) and with no slide under `prefers-reduced-motion`.
5. The "Catch up" card (`CatchUpCard`, `catch-up-state.ts`). It shows while the shared prop `catchUp` holds a date and `GET /communities/{community}/catch-up` returns lines: first card of the home of a community, top of the panel (the community of the page) and one per community on the page "Notifications". A region with the heading "Catch up", lines of 2 lines of text each as one link, no count. "Show all" (when `has_more`) opens the panel from the home and moves the focus to the heading "Needs you" in the panel and on the page. "I am caught up" calls `POST /notifications/caught-up`, hides every card (a module value, because the prop of the open page is stale), clears the "Following" list, says "You are caught up" in a status region that outlives the card, and moves the focus to the heading under the card (the main heading of the page on the home). The user menu has "Catch up" while the date is there.
6. The dots of the navigation (`SpaceNavigation`). `has_new` gives a dot with a border in the color of the text (forced colors keep it) and "New content" in the name of the link; a chat space shows its number only when `notification_level` is `all`; a muted space shows nothing. The server writes the visit when the page of the space opens, so the dot is gone with the next page data.
7. The page "Notifications" (`Pages/Notifications/Index.tsx`, route `notifications.index`, `NotificationsPageController`): the heading "Notifications", the cards, then the same `NotificationsPanel` with `variant="page"` (headings at level 2, no link to itself). The panel ends with "Open the Notifications page".

## Tests

Vitest and Testing Library, in `*.spec.tsx` files next to the component. Test the behavior the member sees: roles, labels, keyboard. Run them with `npx nx run-many -t test`.
