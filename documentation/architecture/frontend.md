# Front-end design

The front-end is a React 19 application rendered through Inertia.js 3. Laravel decides which page to show and with which initial data. React renders it, and talks to the REST API for every change.

## Pages

1. A page is a component in `apps/knowii/src/Pages/<Area>/<Name>.tsx`, rendered by an Inertia controller (`app/Http/Controllers/Inertia`) or by `Route::inertia(...)` in `routes/web.php` for static pages. The list of pages is `pageComponents` (`apps/knowii/src/page-components.ts`): it leaves the spec files out, so the production build never ships a spec file as a page (#1552).
2. The controller passes the initial data as props. The props interface of the page and the array in the controller must stay aligned (both carry a `WARNING` comment).
3. Every page renders inside `<AppLayout>`, which gives the header, the breadcrumb, the page actions and the footer. Community pages also render `<CommunityShell>` (`Components/Spaces`): the space navigation in a sidebar on desktop and in a drawer on mobile, reloaded when the space tree changes.
4. Further data and every change go through the Knowii API client, never through Inertia form posts. The API stays complete.
5. Links use Inertia `<Link>`. A link that changes the URL without a reload sets `preserveState={true}`.
6. A visitor (nobody signed in, `page.props.auth.user` is null) reads the public spaces through five pages: the space, the post, the page or lesson, the resource and, since #1514, the event ([ADR 0044](../adr/0044-public-spaces-for-visitors.md), [ADR 0053](../adr/0053-events-a-space-type-with-its-own-table.md)). `<AppLayout>` gives them "Sign in" and "Sign up" in place of the user menu and no dashboard link, and tells the components below it through `VisitorProvider` (`Components/Reader`). `<SignInPrompt>` ("Sign in to reply", "Sign in to post", "Sign in to download") takes the place of a composer or of the download. Reactions are counts, and no member name is a link. The props are cut by the server: the client never hides what it received. The public page of a community (#1485, `Pages/Communities/Public.tsx`) is one more page: a visitor and a signed-in outsider get it instead of the community home, with the name, the description, the navigation of the public spaces and the newest public posts, and the way in of an open community (#1486): `<JoinCommunity>` (`Components/Communities`) shows "Join" to a signed-in outsider and "Sign up to join" and "Sign in" to a visitor, on this page and in the header of a public space, and nothing for a member or when the community is by invitation (`community.join_policy`). It does not join by itself after a sign-up, keeps the focus while it works (`aria-busy` and a guard, never `disabled`) and shows the refusal of the server in an alert. The settings page has the card `<JoinPolicySetting>` (owner and admins) and the member management lists the removed members with "May join again". In the breadcrumb of a visitor "Home" goes to `/` (the layout does it), and the community to this page. A public space shows no notice to its members (#1493); the texts of the space form for a manager are in `Components/Spaces/PublicSpaceNotice.tsx`.

## Rendering errors

A component that throws while rendering does not blank the page. `<ErrorBoundary>` (`@/Components/ui`) catches the error, logs it to the console and shows a fallback:

1. `<AppLayout>` wraps the page content: the header, the navigation and the footer stay, the content shows "Something went wrong on this page" with "Try again" and "Reload the page". An Inertia visit to another URL clears the error (`resetKey={page.url}`).
2. `main.tsx` wraps the whole application, for an error in the layout itself.
3. Member content uses the block variant, so one broken item does not hide the others: each post card, the post body, each comment (`<ErrorBoundary variant="block" label="this post">`). Wrap new member content the same way (chat messages, pages, lessons).

## Global data

1. Data that every page needs (the current user, the communities of the user) comes from `HandleInertiaRequests`.
2. Client-side state that every page needs lives in the React context of `libs/common/src/lib/contexts/app-context.tsx`. Example: `showToast()`. The provider keeps the toasts, and the `<Toaster>` (mounted once in `main.tsx`) shows them. A toast survives an Inertia visit. A toast can offer one link to the next step (`action`, for example "Open the space" after a new space, #1576): it stays until the person follows the link or closes the toast, and when a toast that has the focus goes away, the focus goes back to the element that had it before.
3. The values of the instance (#1653, [ADR 0055](../adr/0055-instance-values-come-from-configuration.md)) come in the shared prop `instance` (`InstancePageProp`): `contactEmail`, `publisher`, `footerNote`, `footerLinks` and `socialLinks`. The server builds it from its configuration (`App\Support\InstanceValues::pageProp()`). The footer, the contact page and the account deletion texts read it, and hide what an empty value feeds: no `©` line without a publisher or a note, no mail icon and no "Contact us" without a contact address, no social icon without a social link. `buildFooterLinkGroups(instance)` (`libs/common`) builds the link columns of the footer. No component holds a name, an address or a link of one instance: `libs/common/src/lib/metadata.json` keeps only the address of the repository.
4. The legal pages that the instance has a text for (#1653, the part "The legal texts" of ADR 0055) come in the shared prop `legalPages` (`LegalPageSlug[]`, from `App\Support\LegalPages::available()`). `LEGAL_PAGE_SLUGS` (`constants.ts`) lists the six slugs, aligned with `LegalPages::PAGES`. A page that is not in the prop answers 404, so nothing links to it, and without the prop no text exists. `buildFooterLinkGroups(instance, legalPages)` puts only the pages that exist in the "Legal" column and leaves the column out when none exists; the compact footer follows. The sign-up box (`Register`) and the text under the sign-in button of the provider (`OpenIdConnectButton`) name the terms and the privacy policy, one of them, or only the minimum age. `NewsletterForm` says "See the privacy policy." only with `privacy-policy`. `CreateCommunityDialog` shows its two lines about the agreement only with `dpa`. A new place that links to a legal page checks the prop in the same way.

## UI components

1. The building blocks live in `apps/knowii/src/Components/ui` and are imported from `@/Components/ui`: buttons, form controls, dialog, drawer, menu, select, combobox, cards, avatar, badge, link tabs, cover image, toasts and more ([ADR 0003](../adr/0003-own-ui-components.md)).
2. Use them instead of styling raw elements. A new building block goes there, with a Vitest test (`*.spec.tsx`), keyboard support and a visible focus ring.
3. Headless UI is used only for the accessible interactive parts (dialog, listbox, combobox, menu, switch). Everything else is plain React and Tailwind CSS.
4. Feature components (a post card, a space navigation) live in `apps/knowii/src/Components/<Feature>/` and compose the building blocks.
5. A setting that saves at once, without a "Save" button, is a `Switch` (#1569), with a `SaveStatus` next to it: "Saving", then "Saved", or the error, and the control shows the old value again (`useInstantSave` holds the value, the busy state and the status). A choice of several values that saves at once (who can join) keeps its radios and gets the same status. A `Checkbox` is only for a form with a "Save" button. A change that widens access (a community open to anyone with an account, indexing on) asks first with a `Dialog`: nothing is saved before the yes, and "Cancel" and Escape leave the control as it was.

### Toolkit

The building blocks have stories in Storybook ([ADR 0049](../adr/0049-component-toolkit-storybook-stories-as-tests.md), #657). The configuration is in `apps/knowii/.storybook/`.

1. Run it in the container: `npm run storybook` (the dev server on port 6006, open `http://localhost:6006` on the host; the port is `STORYBOOK_PORT` in `docker-compose.yml`) or `npm run storybook:build` (the static site in `dist/storybook`). The toolbar switches the theme (dark first) and the width (360 px, 1920 px). The accessibility panel checks the contrast, which the tests cannot do. The catalogue of the branch `main` is public, at `https://knowii-oss.github.io/knowii/` (point 12).
2. Add a story: create `Components/ui/<Name>.stories.tsx` next to the component, in the CSF 3 format with types (`satisfies Meta<typeof Name>`). Write one story per variant and state: kinds, sizes, with and without an icon, disabled and `aria-disabled`, busy, error, long text, as the component has them. The comment of the meta says when to use the component and its accessibility contract. A keyboard path is a `play` function that uses `storybook/test`, with `within(canvasElement)`, or `within(dialog)` for a dialog (it renders in a portal on the body, and jsdom does not make the page behind it inert).
3. The stories are tests: `stories.spec.tsx` renders every story, runs its `play` function and runs `axe-core` on the page, with the other Vitest tests. Only `color-contrast` is off, because jsdom computes no colors.
4. The guard, `stories-guard.spec.ts`, fails when a component file has no story file or a story file has no story. Every component has its story file (#657): a new component comes with its stories in the same pull request.
5. A story renders without the application around it. The link stories of `Button` stop the visit in their `onClick` (a plain `<a>` without a `ToolkitProvider`, or the Inertia link with it); do the same for another component with a link. A story that shows the part of the application (the video player of `MarkdownContent`) gets it from a decorator with `ApplicationToolkitProvider`.
6. A list that opens (the list of `Select` and of `Combobox`, the menu of `DropdownMenu`) renders in a portal inside the landmark of its button, or inside its dialog, never on the body (#1651): `useLandmarkPortalTarget` (`landmark-portal.ts`) gives the target of a Headless UI `Portal.Group`. The page and the stories then pass the axe rule `region` with the list open, without a workaround.
7. The boundary (#657, point 2.5 of the [proposal](../design/component-toolkit/proposal.md)): a file of `Components/ui` (not its specs and stories) imports only `react`, `react-dom`, `@headlessui/react`, `react-icons/*`, `@knowii/common`, `classnames`, `tailwind-merge`, `date-fns` and the other files of the folder (`./Name`). Anything else is a lint error: `@inertiajs/*`, `ziggy-js`, an `@/` path, a relative path out of the folder. The rule is `no-restricted-imports` in `apps/knowii/eslint.config.mjs`, scoped to the folder; `boundary.spec.ts` proves it with the ESLint configuration of the project. The toolkit can move to a library as a move of files.
8. A component that needs a part of the application gets it from the toolkit context (`ToolkitContext.tsx`): `useToolkit()` gives `linkComponent` (the link of `LinkButton`, `Breadcrumb` and the action of a toast) and `videoRenderer` (the player of a video block of `MarkdownContent`). The defaults work without the application: a plain `<a>` (a `<button>` for `as="button"`, the link of a request that is not a GET) and a plain link to the video. The application sets the values once, where the Inertia app starts: `main.tsx` renders `ApplicationToolkitProvider` (`Components/ApplicationToolkit.tsx`) with the Inertia `Link` and the click-to-load `VideoPlayer`. A `ToolkitProvider` inside another one changes only the values that it gives. One place that needs another value gives it as a property (`linkComponent` of `LinkButton` and `Breadcrumb`, `videoRenderer` of `MarkdownContent`). A new part of the application goes in the context the same way, never as an import. A test that needs the Inertia link or the player renders `ApplicationToolkitProvider` (`wrapper` of `render`).
9. Four blocks for long lists and for the lists of items (#657 slice 4, #1666), each with its stories. `Combobox`: a choice of one option in a long list, with a text field that filters at each key (Headless UI Combobox; for a short list use `Select`). Its default filter (`comboboxOptionMatches`) finds any part of the label or of a keyword of the option, ignores the case and the accents, and takes spaces, underscores, slashes and other punctuation as the same; the labels that start with the text come first. `pinned` keeps values at the top while the field holds no search text. The list renders 50 options at most (`COMBOBOX_MAX_OPTIONS`), then "Type to see more": a list of hundreds of options stays fast, and no virtual list is needed. A polite status says the number of results after each change of the list. Enter picks; Escape, Tab and a click outside keep the old value; closed, the field shows the label of the value, selected, so that the next key starts a new search. The name comes from `aria-labelledby` (the id of the visible label) or `aria-label`: the type asks for one of them. An error: `invalid` sets `aria-invalid` on the field, and `aria-describedby` names the text of the error, which the form shows. `Badge`: a short text label for a state ("Draft", "Cancelled"), a `span` whose text carries the meaning; the variant (`neutral`, `info`, `success`, `warning`, `danger`) colors only the border and the icon, and the text keeps the color of all text. `LinkTabs`: a navigation with links to the views of one page that each have an address ("Upcoming", "Past"); the open view has `aria-current="page"`, a line under it and a heavier text; it is not the tabs of ARIA, and the links wrap on a narrow screen. `CoverImage`: a picture in a 16:9 box with the corners of a `Card`, and a neutral placeholder of the same size without an address or when the picture cannot load.
10. Five small blocks that the feature components wrote by hand before (#657 slice 4b), each with its stories. `Skeleton`: the grey lines that hold the place of a list while it loads (`rows`, `lines`, `avatar`); a polite status (`role="status"`) whose only text is the `label` for screen readers ("Loading your notifications"), with the shapes hidden from them; the pulse runs only with `motion-safe`, each shape has a border in forced colors, and nothing takes the focus. It is a `div`, never a child of a `ul`, and it must not sit inside an element with `aria-busy`: assistive technology may ignore what a busy element holds, and the label with it. `LoadMoreButton`: the row with the secondary button that loads the next part of a list ("Load more", "Load older"), under the list or above it (`size`, `align`, `aria-label` when a page has several); while it loads (`loading`) the button has `aria-busy` and `aria-disabled`, shows the spinner of `Button`, keeps the focus and ignores a click, Enter and Space. The feature component shows it only while the list has more. The rule for the result: the feature component must say what loaded in its own status region. `NotificationsPanel` and `EventList` do it today; `PostList`, `ResourceList`, `CommunityMembersManager` and `AccessGroupsManager` do not do it yet. `QuestionBanner`: one plain band at the top of a page that asks one question with two answers (the time zone question of `TimeZoneAsk`); a region named by the question, which is a paragraph and not a heading; the answer that changes something comes first, an error shows after the buttons as an alert, the banner never takes the focus and has no close button (each answer closes it). Not a dialog and not a toast. `CountBadge`: the number of new things on a link or a button, a `span` that renders nothing at zero or less; `max` gives "9+"; with `label` a screen reader hears "3 unread" as a part of the name of the link, and without `label` the badge is `aria-hidden` and the control must hold the number in its own name (the bell: "Notifications, 3 new"); `placement="corner"` puts it on the corner of an icon button. The navigation and the messages have no maximum, the bell has 9. Not a label (`Badge`). `Dot`: a small round mark next to an item, `tone="new"` (a space with new content; its border has the color of the text, so forced colors keep it) or `tone="online"` (the corner of an avatar); the shape is always `aria-hidden`; with `label` its text is for screen readers and becomes a part of the name of the link (", New content"), and without `label` it is decoration: the item says the same thing in words elsewhere. Never a control, never the only sign of a state.
11. Three blocks of the forms and of the lists of cards moved in from `Components` (#657 slice 4c), each with its stories; import them from `@/Components/ui` as the other blocks. `InputLabel`: the visible label of a form field, a `label` above the field. With `htmlFor` (the id of the field) it is the name of the field, and a click on it puts the focus in the field; for a group of controls that is not one field (the radios of a `SegmentedControl`), it gets an `id` that the group names in `aria-labelledby`. Not a heading, not a hint and not the `legend` of a `fieldset`. `InputError`: the text of the error of one form field, under the field. It renders nothing without a message and without children, so a form always renders it; the message is a paragraph with `role="alert"`, which a screen reader says when it shows. The contract: it gets an `id`, and the field names that id in `aria-describedby` and is `invalid`, so that the message is the description of the field. Many callers do not give the `id` yet. Not the status of a save (`SaveStatus`) and not a hint. `CardGroup`: the grid of a list of cards (the communities of the dashboard), one column on a phone, then as many columns of 20 rem or more as the width holds. It is a `ul`: each child must be an `li` that holds one card. `Separator` is gone: use `<Divider className="my-10" />`, which is what it rendered.
12. The catalogue (#657 slice 5): the built Storybook of the branch `main`, public at `https://knowii-oss.github.io/knowii/`. The docs page of a block comes from its story file (the tag `autodocs` of `preview.tsx`): its text is the docblock above the `meta` (when to use the block, when not, its accessibility contract), then come the table of the props and the stories. No `.mdx` file per component, and no copy of a docblock. A documentation page is an `.mdx` file, `Components/ui/docs/<Name>.mdx`: `main.ts` loads the pages with the stories. A page starts with `import { Meta } from '@storybook/addon-docs/blocks';` and `<Meta title="..." />`. The title is `Introduction` (`docs/Introduction.mdx`, the first page of the catalogue) or `Rules/<Name>` (a rule page), and `storySort` of `preview.tsx` gives the order of the list: `Introduction`, `Rules`, `Components`. The title of a component (`Components/ui/<Name>`) is a part of public addresses: it does not change. A page holds text, links and the doc blocks of Storybook only. A live example in a page is a story of a story file, shown with `<Canvas of={...} />`, so that it stays a test: no component code in a page, and no `.tsx` helper in `docs/`. A link to a document of the repository is a full `https://github.com/knowii-oss/knowii/blob/main/...` address. A link to another page of the catalogue is relative (`./?path=/docs/components-ui-button--docs`), never an address that starts with `/`: the site lives under `/knowii/`, and the build needs no setting for it. A Markdown table needs a package that is not installed: write an HTML `table`. `preview-head.html` gives the lists of a page their numbers and bullets back, which the styles of the application take off. What the tests see: the lint, the type check, `stories.spec.tsx` and the guard do not read an `.mdx` file, so only the Storybook build (`npm run storybook:build`, which CI runs on each pull request) proves that a page compiles. `catalogue.spec.ts` reads the pages and the story files as text: it fails when a page has no `<Meta title="..." />` or another kind of title, and when a page or a story file holds an email address that is not in `example.com`, `example.org` or `example.net`. What the catalogue must not hold, because it is public and built from the repository alone: a secret, a token or a key; data of a real person (a real name, a real email address, a real picture of a person); an address of an internal server; a call to another origin when a page opens (the fonts and the pictures come from the build, and a video loads only after a click). The spec checks the email addresses and the secret scanning of the repository checks the secrets: the rest is a rule for the review. The publication: `.github/workflows/toolkit.yml` builds the Storybook and deploys it to the page site of the repository on each push to `main`, and by hand from `main` only. It never runs for a pull request (CI builds the Storybook there, and nothing is published) and never on a fork. The build job runs the code of the repository with a token that only reads; the deploy job holds the rights of the page site and runs no code of the repository; the environment `github-pages` lets only `main` deploy. `main.ts` sets `disableProjectJson`: the site holds no file with data about the tools of the build. Search engines do not index the catalogue: `manager-head.html` and `preview-head.html` hold `<meta name="robots" content="noindex" />` (a `robots.txt` has no effect under a sub-path).

Member content: `MarkdownContent` shows the HTML that the server renders. It replaces each `div.video-embed` block (a YouTube or Vimeo link alone on its line, [ADR 0031](../adr/0031-videos-in-member-content.md)) with the `videoRenderer` of the toolkit, in the application the click-to-load `VideoPlayer`. The `MarkdownEditor` has an "Add a video" button that checks the address with `parseVideoUrl` (`libs/common`).

Images in the editor (#1207): the image button, a paste or a drop takes up to 10 images at a time. `ImageInsertPanel` lists them with a preview, a required description (the alt text), the state of each upload, and buttons to reorder and remove. "Insert the images" uploads them one after the other and writes them one per line; nothing goes in the text before every upload worked, and a second try uploads only the images that failed.

Galleries ([ADR 0039](../adr/0039-images-that-follow-each-other-form-a-gallery.md)): the server writes the images that follow each other as `div.image-gallery`, with each image as a link to its file. The grid is CSS only (`.image-gallery` in `styles.css`, chosen from `data-image-count`), so there is no layout jump when the script starts. `MarkdownContent` listens to the clicks on its content and opens `ImageViewer` (Headless UI Dialog): the image on the whole screen, its alternative text as the caption, previous and next with the buttons, the arrow keys, Home, End and a swipe, and "Open the original". A click with a modifier key stays a normal link. A rich block that only needs a shared dialog follows this pattern; a block that needs its own component gets a React root, like the videos.

## Themes and tokens

1. Colors, fonts and breakpoints are the Knowii brand tokens defined with `@theme` in `apps/knowii/src/styles.css`. The default Tailwind palette is disabled. The Noto Sans font comes from the `@fontsource-variable/noto-sans` package: `main.tsx` imports its CSS and Vite bundles the WOFF2 files, so the font is served from the Knowii origin. Never load a font or a stylesheet from a font service (#1341, GDPR): the CSP allows none.
2. Two themes: dark (default) and light, selected with `data-theme` on `<html>`. The inline script in `app.blade.php` applies the saved choice before the first paint. `useTheme()` and `<ThemeToggle>` change it.
3. Tokens change with the theme: never hardcode `white` or `black`. Check every screen in both themes.
4. Contrast (#1562, #1568, #1613). The comments of `styles.css` give the contrast of each dark text token on background / surface / surface-elevated / well, and `contrast.spec.ts` checks every pair that the application uses (WCAG 2: 4.5:1 for text, 3:1 for large text and the borders of controls; a token with an alpha is blended on the surface first). Pink text and a border that marks a state (the open entry of the menu, the open tab of the editor, a reaction of the member) use `secondary-text`; `secondary` (#e5007d) is for fills, buttons and the logo. In the dark theme, `text-gradient-brand` has lighter stops of the same hues, so the whole gradient reaches 3:1 on the background. The dark background color is also in `THEME_BACKGROUND_COLORS` (`constants.ts`) and in the `theme-color` meta tags of `app.blade.php`.

## Content Security Policy

The policy has no `'unsafe-inline'` for scripts or styles ([ADR 0007](../adr/0007-strict-content-security-policy.md)):

1. Set styles with classes, or with React `style` props (they go through the CSSOM, which the policy allows).
2. Never call `setAttribute('style', ...)`, and never add a `<style>` element without the nonce from `<meta property="csp-nonce">`.
3. Third-party scripts are added by our own code (`'strict-dynamic'`). Avoid embeds that inject styles.
4. Images, media, frames and connections go only to the origins listed in `config/secure-headers.php`.

## Data and validation

1. Zod schemas in `libs/common/src/lib/types` describe the entities (`community.schema.ts`) and in `libs/common/src/lib/api` the requests and responses (`create-space-request.schema.ts`).
2. Forms use react-hook-form with the Zod resolver. The limits come from `libs/common/src/lib/constants.ts`, aligned with `App\Constants`.
3. The Knowii API client (`libs/common/src/lib/api/knowii-api-client.ts`) is the only place that calls `fetch` for the API. API paths are constants in `constants.ts`. New methods use `apiRequest()` (`api-result.ts`): it parses `data` with a Zod schema and returns an `ApiResult` (`ok`, `data` or `message` and field `errors`), never throws.

## Real time

`useSocket` (`libs/common/src/lib/hooks/use-socket.ts`) wraps Laravel Echo. A page names a channel and the events it wants, and gets typed payloads. The event names match `broadcastAs()` on the back-end. Each hook removes only its own listeners when it unmounts, and the channel is left when its last user unmounts, so several components can listen on the same channel. A visitor opens no connection: the hook takes `enabled`, which a page or component sets to false for a visitor, and `window.Echo` (`bootstrap.ts`) is created on its first use, because creating it opens the connection. Pages merge incoming events into their state (by `cuid`, so a duplicate is ignored) without losing what the member is typing.

## Notifications: the bell and the panel

The bell and its panel (#1484, [ADR 0042](../adr/0042-notifications.md), design 5.1, 5.2, 6.12 and 9) are in `Components/Notifications`. They show "Needs you" and, since #1497, "Following" (the level 2 lines). `<AppLayout>` renders them for a signed-in member, on every page. A visitor gets no bell, no count request, no socket and no live region.

1. One source of truth for the number. `NotificationsProvider` holds the count, and the count is always the value of the server (`GET /notifications/count`). It is loaded on page load, when the window gets the focus, when the socket reconnects (`useSocketReconnected`) and after each `notifications.changed` event of the channel `user.{cuid}`. The client never adds 1. Events of a short time give one request (a trailing debounce of 300 ms), and a late answer never replaces a newer one. The bell name holds the number ("Notifications, 3 new", "Notifications, 9 or more new") and the badge (1 to 9, then "9+") is hidden from assistive technology.
2. The panel mounts when it opens, so each opening loads the list again (`use-notification-feed.ts`: 20 lines per page, "Load older", and "Earlier" behind a closed disclosure, loaded the first time it opens, never counted: the list that was "Older" before #1476). On a desktop it is a non-modal region under the bell: Tab leaves it, Escape and a click outside close it. Below the `md` breakpoint (960 px, the phone layout of the app) it is the `Drawer` component. The focus goes to the heading "Notifications" on opening, and back to the bell on closing.
3. A line is a list item with one link and real buttons (`NotificationLine`). The link goes to the exact item (`notification-link.ts`): `#comment-{cuid}` on the post page or the resource page (the permalinks of #1205), and `?thread={cuid}#message-{cuid}` on the chat space. `ChatRoom` follows that address: it opens the thread, or loads older messages (10 pages at most) until the message is there, and gives it the focus. The target of a jump keeps a visible outline until the focus leaves it. A line that is not seen yet shows "New" in bold, never by color alone. The word stays while the panel is open.
4. Seen: a line that stayed visible in the open panel for one second (an `IntersectionObserver`, or every line when the browser has none) is marked seen. One request holds all the lines of that moment, then the count is loaded again.
5. "Done" marks the row read and removes the line. The status text of the panel (polite) says "Done. Undo" for 8 seconds. "Undo" puts the line back; a 422 (a newer notification exists) reloads the list. The focus goes to the next line, else the line before, else the heading. The buttons of a line never use `disabled`: they use `aria-disabled` and `aria-busy` with a guard, and keep the focus.
6. An event while the panel is open never moves the list. Lines that arrived wait behind "2 new. Show". A line that another device marked done and that has the focus stays, marked "Done on another device", until the focus leaves it.
7. One polite live region exists from the load (in `NotificationsProvider`). It says the actor and the verb of a new level 1 row that the member did not see ("Ben replied to your post"), once per 30 seconds at most. Several arrivals of the window become "3 new for you". It never announces a change of the count. Nothing uses `assertive`.

## Events (#1514, #1515, [ADR 0053](../adr/0053-events-a-space-type-with-its-own-table.md), [design](../design/events/design.md) 4, 6.1 to 6.4, 6.7 and 11)
